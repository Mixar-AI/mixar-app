# Self-Update (`modules/common/updates/`)

One **Restart & Update** click stages the release installer, spawns a detached helper, quits, and relaunches; the downloads page is the fallback. Where no administrator prompt is needed (`InstallLocation.needs_elevation` False: macOS; every Windows install is per-machine, so not Windows yet) a ready update also installs when the user quits (`exit_pre` → `core/silent_install.py`, helper in no-relaunch mode) or, after a session that never quit normally, at the next launch (`core/launch_install.py` from `staged-update.json`, `core/staged_record.py`; only the copy whose install location the record names as `target` — staging is per user); both go through `silent_refusal` (setting `install_updates_on_quit`, a signature verified in this process against a pinned signer — on macOS the running app's own Team ID, so unsigned/dev builds keep Restart to Update — failures, `install_gate.silent_blocker`; the launch re-verifies on a worker thread, never trusting the record, refuses a record older than 24 h, installs only once its own update check (`trigger.request_update_check`) has answered with the staged installer (version and `sha256`), and every answered update check deletes a staged download it no longer offers — `launch_install.forget_unoffered`; the macOS helper pins the installed bundle's own Team ID and, for these silent installs, waits up to 60 s for anything still running from the bundle — `stage=locked` — and never swaps past `HELPER_SWAP_DEADLINE_S` — `stage=expired`) and the one start path `core/install_start.py` (one helper per process: the launch install's quit can find the update READY again), and telemetry carries `trigger` (`click`/`quit`/`launch`). Decisions live in `core/install_flow.py` (`plan_restart`, `apply_and_restart`) so they are testable under the `bpy` mock; config is `mixar.json` → `updates.{channel,check_delay_seconds,auto_download,downloads_url}`. Install paths carry no version (pinned by `tests/test_update_packaging_paths.py`). Windows staging lives in `%ProgramData%\Mixar\Updates` (a per-machine MSI runs elevated and must read the installer from a shared location); the installer is trusted only after the backend `sha256` matches AND its signature matches the running app's (`core/verify.py`, which also returns the signer's certificate thumbprint); the detached helper never lives in the install directory; a quit that does not happen is recovered by a 15s watchdog that returns state to READY. On Windows only the MSI-registered copy self-installs (`app_paths.classify_windows_install`; others get the browser). Before quitting, `core/install_gate.py` checks who runs from the install dir through a native Win32 process table (`core/win_processes.py`: Toolhelp snapshot + image path + creation time + visible windows, no subprocess, PID-reuse-safe parent links): other Mixar windows / other programs get the "Close other apps to update" toast; Mixar's own background work (our descendants, windowless `mixar.exe -b`) gets a "Finishing background work" toast plus a 2 s timer that continues the update once clear (Cancel; bounded by `BACKGROUND_WAIT_MAX_S`); only once the update goes ahead are Mixar-connector pythons (an AI app's MCP server, live or abandoned — stateless and stale after the restart, the app respawns or reconnects it) ended, never while the update then stops or on every poll of the wait; one that could not be ended is named in the toast. Once the helper runs, the connector's `updating` marker (`mcp_bridge.core.installation.mark_updating`, cleared by the relaunched app's relay or an aborted quit, 900 s bound; a launch blocked mid-install calls `keep_updating()` first so its own relay leaves it) stops a fresh connector from cold-starting the old binary. Helper v6 (records the trigger; can leave Mixar closed after an install on quit, reopening it only for a launch turned away meanwhile — `update-reopen-requests.txt`) runs the MSI with `/passive` (no files-in-use prompt can stall it), ends connector pythons respawned since the gate ran, waits for the install dir as a safety net, runs every tool by its System32 path with delayed expansion off, pins the re-verify to the verified signer thumbprint, keeps the previous MSI log as `msi-install.prev.log`, records registry version/location and relaunches from `InstallLocation`; `purge_stale` never deletes the logs (it trims `update.log` past 1 MB). The app writes `update-in-progress.json` after spawning the helper (`core/install_marker.py`); the helper deletes it on every exit path just before relaunching. While it names a live helper (PID + creation time, under 15 min), a Mixar opened by hand from the copy it installs (the marker's `target`; another copy starts as usual) toasts "Mixar is finishing an update" and quits before the result report / update check (`bootstrap/update_checker.py`), and `purge_stale` touches nothing; a stale marker is deleted, one that cannot be judged (unreadable, a failed lookup) blocks nothing but is kept and keeps guarding the purge until the file is older than the cap. The next launch classifies the result (`installer.classify_result`, `core/result_report.py`: success / pending_reboot / no_effect / failed + `failure_reason`); a 3010 whose target version runs is `success` only when `PendingFileRenameOperations` queues no rename into the install directory (`core/pending_renames.py`, one `winreg` read, passed in so `classify_result` stays pure) — contracts in `docs/modules/self-update.md`.

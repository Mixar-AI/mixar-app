# Self-Update (`modules/common/updates/`)

One **Restart & Update** click stages the release installer, spawns a detached helper, quits, and relaunches; the downloads page is the fallback. Decisions live in `core/install_flow.py` (`plan_restart`, `apply_and_restart`) so they are testable under the `bpy` mock; config is `mixar.json` → `updates.{channel,check_delay_seconds,auto_download,downloads_url}`. Install paths carry no version (pinned by `tests/test_update_packaging_paths.py`). Windows staging lives in `%ProgramData%\Mixar\Updates` (a per-machine MSI runs elevated and must read the installer from a shared location); the installer is trusted only after the backend `sha256` matches AND its signature matches the running app's (`core/verify.py`, which also returns the signer's certificate thumbprint); the detached helper never lives in the install directory; a quit that does not happen is recovered by a 15s watchdog that returns state to READY. On Windows only the MSI-registered copy self-installs (`app_paths.classify_windows_install`; others get the browser). Before quitting, `core/install_gate.py` checks who runs from the install dir through a native Win32 process table (`core/win_processes.py`: Toolhelp snapshot + image path + creation time + visible windows, no subprocess, PID-reuse-safe parent links): other Mixar windows / other programs get the "Close other apps to update" toast; Mixar's own background work (our descendants, windowless `mixar.exe -b`) gets a "Finishing background work" toast plus a 2 s timer that continues the update once clear (Cancel; bounded by `BACKGROUND_WAIT_MAX_S`); only once the update goes ahead are Mixar-connector pythons (an AI app's MCP server, live or abandoned — stateless and stale after the restart, the app respawns or reconnects it) ended, never while the update then stops or on every poll of the wait; one that could not be ended is named in the toast. Once the helper runs, the connector's `updating` marker (`mcp_bridge.core.installation.mark_updating`, cleared by the relaunched app's relay or an aborted quit, 900 s bound; a launch blocked mid-install calls `keep_updating()` first so its own relay leaves it) stops a fresh connector from cold-starting the old binary. Helper v4 ends connector pythons respawned since the gate ran, waits for the install dir as a safety net, runs every tool by its System32 path with delayed expansion off, pins the re-verify to the verified signer thumbprint, keeps the previous MSI log as `msi-install.prev.log`, records registry version/location and relaunches from `InstallLocation`; `purge_stale` never deletes the logs (it trims `update.log` past 1 MB). The app writes `update-in-progress.json` after spawning the helper (`core/install_marker.py`); the helper deletes it on every exit path just before relaunching. While it names a live helper (PID + creation time, under 15 min), a Mixar opened by hand toasts "Mixar is finishing an update" and quits before the result report / update check (`bootstrap/update_checker.py`), and `purge_stale` touches nothing; a stale marker is deleted, one that cannot be judged (unreadable, a failed lookup) blocks nothing but is kept and keeps guarding the purge until the file is older than the cap. The next launch classifies the result (`installer.classify_result`, `core/result_report.py`: success / pending_reboot / no_effect / failed + `failure_reason`) — contracts in `docs/modules/self-update.md`.
